# 任务交接与认领

本页是云中立理念在「多 Agent 协作」方向的落地章：任务本身也是一种资产，它的归属、格式与流转规则，决定了协作能不能跨工具延续。

## 一、问题

多个 Agent（不同厂商、不同运行面）协作时，任务最容易丢在三个地方：

- 任务只存在某个 Agent 的私有记忆或会话里，换一个接手者就断线；
- 任务没有明确的归属者，两个人同时做、或都以为对方在做；
- 完成与否靠口头汇报，没有凭证，事后无法核对。

这三件事，本质都是资产问题：任务没有以开放格式、放在资产所有者自己的地盘上流转。

## 二、原则

1. **任务资产归所有者**：任务的真源存放在所有者自己的仓库中，不存放在任何单个 Agent 的私有记忆、会话或专有系统里。Agent 换代、厂商更迭，任务资产不动。
2. **格式通用、纯文本优先**：任务以任何 Agent 都能直接读懂的纯文本（Markdown / YAML）书写，自带上下文、不用某个工具的内部黑话。接手者不需要原 Agent 在场解释。
3. **一次只许一个执行者（Lease）**：任务被认领后进入独占状态，其他执行者不得并行重复执行；确需转手，先释放、再认领，全程留痕。
4. **认领即承诺（Ownership）**：认领人对该任务的推进与回执负责；认领不是收藏，长期无进展的认领应被释放回待认领池。
5. **完成认回执（Receipt）**：完成判定以可核查的凭证为准——提交哈希、标签、Release、回读结果、文件落点；不认口头汇报。进行中就写进行中，没合并就写没合并。
6. **状态诚实分级**：待认领、已认领、进行中、待验收、已完成，各归其位；证据不足时标「待验证」，不把推测写成事实。

## 三、与 XSA 的关系

上述第 3–5 条即 XSA（XingTu Super Agent）Coordination Guard 的设计要点：Ownership、Lease、Receipt，加上冲突检测与幂等要求。云中立回答「任务资产归谁、用什么格式」，XSA 回答「多个 Agent 之间如何认领与交接不打架」。任务交接系统是两者的第一个共同落地：理念在本仓，规则在 XSA，执行台在私有仓 xingtu-cloud-task（任务卡、认领与回执均在其中流转）。

## 四、最小实现（不依赖任何特定工具）

- 一张任务卡：目标、背景、执行单或材料位置、验收口径、红线；
- 一个状态：五级状态之一，随进展更新；
- 一个认领人：同一时刻唯一；
- 一份回执：完成时附凭证链接，未完成时写明卡点与未尽事项。

任何满足这四项的载体（仓库 Issue、纯文本总表、看板）都算本章的合格实现；载体可换，资产与规则不换——这正是云中立的本意。
